# Agent 行为分析与反馈协议

> 读者：agent（经部署副本）与开发者。本文是 #34 裁决（C 变体）的 L 层落点：会话即完整记录，issue 承载标准化工件。分析由 agent 依据自身 loop 上下文生成。成文于 2026-10-13。

## 反馈处理——行为面，现在有了声明

当用户报告对 agent 行为的不满：

1. **先立即止损**——在会话内停掉出错模式，绝不在分析的同时继续它
2. **判断责任层**——plugin 约束？框架？纯执行？不属于 plugin/kernel 的事 → 不做分析：直接回复用户
3. **同意门**——若可能是 plugin/kernel 问题，向用户提议做自检（推荐，绝不强求）；征得同意才开始
4. **系统性 → 行为分析**（见下）；一次性 → 会话内修复 + 一行 log，不提 issue

这个面此前未声明（一个 e 类规范真空的活样本，#33 的临场处置）。

## 路由——反馈去哪

| 反馈 | 去处 | 判据 |
|---|---|---|
| kernel / 机制 / 投影 / 框架文档 | owfa | 框架契约面 |
| 核心套件 plugin（原框架 plugin，v0.4 拆分后为 owfa-personal 成员） | **owfa-personal** 仓（v0.4 拆分起） | plugin id ∈ owfa-personal `PKG.members` |
| 包成员 plugin（bb 家族、lark 家族……） | 对应的 `owfa-*` 仓 | plugin id ∈ `PKG.members`；仓库地址见 registry INDEX |
| 行为偏差（#34 这个面） | plugin 所在之处 | 行为契约住在 PLUGIN.md |
| 新 plugin 提案 | owfa（孵化；随包落地时随之迁移） | 尚无归属仓 |
| 不清楚 | 提在 owfa；维护者转移 | 兜底（#20 先例） |

## 分诊门——第 0 步，不过门就不分析

① 系统性（同一场景反复出现）？② 可复现（换个会话仍在）？③ 与约束相关（不是纯执行）？三者齐备——否则：会话内修复 + 一行 log，不生成分析。

## 分析标准——七步

**1. 锚定事件。** 定位偏差点。逐字引用：用户指令（U 层）+ 用户的纠正。

**2. 重建行为链（事实层）。** 从 U 层指令出发，列出实际发生的动作，每步四字段：
- **动作**：读了 / 写了 / 调了 / 生成了什么
- **依据**：重新读取的逐字引用（注入行 / AGENTS.md / skill 正文 / PLUGIN.md / 会话上下文）——绝不凭记忆
- **归属 plugin**：无主步骤标「框架 / 系统层」
- **痕迹**：工具调用记录 / 文件读写 / log 条目

只有带可验证痕迹的步骤进这一层；无法确认的步骤挪到第 5 步（解释层）。

**3. 预期行为——两个来源，分开记录。**
- **已声明预期**：重读 plugin 的 L 层（PLUGIN.md 行为契约 owns/activates/offers/withholds、注入行）——引用之，或写「未声明」
- **用户预期**：第 1 步得到的纠正原文

**4. 定位偏差。** 实际 vs 预期，逐项比对。对着已声明预期 = 合规 diff；对着用户预期 = 需求信号。分开列出。

**5. 归因（解释层）。** 五类，可多选，每项带置信度（高/中/低）、约束原文引用、以及若成立时的最小修复：

| 类 | 含义 | 去处 |
|---|---|---|
| a 约束缺陷 | 写错 / 歧义 / 过度执行 | 修 plugin |
| b 约束冲突 | 两个 plugin 指令不一致 | 修 plugin（优先级或措辞） |
| c 未送达 | 成员层退出 / skill 未加载 | 检查层级与依赖链 |
| d 执行偏差 | 约束在场、未被执行（模型侧） | 不是 plugin 问题；记录，不改 |
| e 规范真空 | 没有约束覆盖该行为 | 补行为契约 |

**6. 建议变更。** 最小修复 + 影响半径（还有哪些场景依赖这条约束）。agent 只提议；权衡与决定归开发者。

**7. 工件。** 按 `.github/ISSUE_TEMPLATE/agent-behavior.md` 格式输出完整分析，与用户确认后，按上面的路由表提在归属仓上。

## 红线

- 引用必须回源重读；禁止凭记忆复述约束文本
- 事实层不放推测；一切推测进解释层并带置信度标记
- 归因分类是强制的——不接受笼统的「plugin 有 bug」
- `agent-behavior` 词根（依 #34 术语裁决，与 user-behavior plugin 保持区分）
- 工件落 GitHub issue，永不落实例 wiki

## 跨工作区工作的法域纪律（owner 裁定 2026-11-16）

agent 不被关在一个工作区里——它可以在机器上任何地方工作。唯一约束：**对 B 工作区的写，只在 B 的指令于工作上下文中在场时合法**（cwd 在 B、B 的 AGENTS.md/插件已加载、操作受 B 协议约束）。在 A 的会话上下文里，B 只读——那是无法域写，正是 bridge 红线一直禁止的东西（被约束的是通道，不是 agent）。跨区边界写之前：显式切换法域、重读目标区自己的契约、让目标区的 validate/audit 把关结果。正典文本在 bridge PLUGIN.md（§ 写红线）；本节是同一裁定的行为面。
